# GitHub Issues for Acadia-OS

## C1: A/B OTA Rollback Mechanism Incomplete - Critical

**Severity:** Critical
**Files:** `meta/meta-acadia/recipes-swupdate/rpi5-swupdate-config/files/`
**Issue:** The rollback mechanism is partially implemented but incomplete. If an update fails, devices may not automatically roll back to the previous working slot.

**Problem:**
- `swupdate-bootcheck.sh` only checks if `acadia-client.service` is active, but doesn't verify the service is actually working correctly
- No `upgrade_available` flag is set in U-Boot env by `post-install.sh`
- The boot-watchdog decrements `tries_remaining` but doesn't verify kernel/DTB actually booted properly

**Impact:** A bad update can permanently brick the device without manual recovery.

**Recommendation:**
1. Implement proper rollback using RPi firmware's tryboot mechanism
2. Ensure all required components work together correctly
3. Add health check that runs BEFORE `network.target`, not after `acadia-client.service`

## C2: No SWUpdate Image Signing - Critical

**Severity:** Critical
**Files:** `Makefile` (lines 296-312), `meta/meta-acadia/swupdate/sw-description`
**Issue:** SWUpdate packages are unsigned by default - any attacker on the network can push malicious updates.

**Problem:**
- `make swu` target only warns but continues if no private key found
- `swupdate.cfg` has no `signingalg` or key configuration
- Unsigned packages can be pushed to any device

**Impact:** Any attacker on the network can push malicious updates to any device.

**Recommendation:**
1. Generate RSA-4096 keypair and store private key in CI secrets
2. Commit only public key to repository
3. Modify `make swu` to FAIL if no private key exists
4. Add signing configuration to `swupdate.cfg`

## C4: Default SSH Password in Documentation - Critical

**Severity:** Critical
**Files:** `README.md` (line 308), `meta/meta-acadia/recipes-core/images/core-image-full-cmdline.bbappend` (lines 104-110)
**Issue:** Documentation shows default password 'rpi' for user 'rpi' which contradicts the locked user implementation.

**Problem:**
- `README.md` line 308 documents: `Username: **rpi** / Password: **rpi**`
- `core-image-full-cmdline.bbappend` shows user is locked (`usermod -L rpi`)
- The comment says "LOCKED (no password). SSH key access only" but the README contradicts this

**Impact:** Any device running this image has a known default password that grants root access.

**Recommendation:**
1. Remove password hash entirely - user should have no password
2. Document that SSH keys must be provisioned at build time or first-boot
3. Ensure `PasswordAuthentication no` is in sshd_config (it is - verified)
4. Consider making `rpi` user a service account (no sudo) with separate admin provisioning

## H2: SWUpdate Web UI Unauthenticated - High

**Severity:** High
**Files:** `meta/meta-acadia/recipes-swupdate/rpi5-swupdate-config/files/swupdate.cfg`, `meta/meta-acadia/recipes-swupdate/rpi5-swupdate-config/files/swupdate-start.sh`, `meta/meta-acadia/recipes-swupdate/rpi5-swupdate-config/files/swupdate-webui-auth-init.sh`
**Issue:** Web UI authentication is not enabled by default.

**Problem:**
- `swupdate.cfg` has no authentication configuration
- `swupdate-start.sh` checks for `/etc/swupdate/webui.passwd` but only sets auth if file exists
- First-boot `swupdate-webui-auth-init.sh` generates credentials but runs after `swupdate.service` (dependency issue)
- Web UI listens on port 8080 over plain HTTP with no TLS

**Impact:** Anyone on the network can push updates without credentials.

**Recommendation:**
1. Ensure `swupdate-webui-auth-init.sh` runs before `swupdate.service` starts
2. Add authentication configuration to `swupdate.cfg`
3. Add HTTPS/TLS support for web UI
4. Consider network isolation requirements for production

## H3: Kernel/DTB Handling in OTA May Be Complex - High

**Severity:** High
**Files:** `meta/meta-acadia/swupdate/sw-description`, `meta/meta-acadia/swupdate/pre-install.sh`, `meta/meta-acadia/recipes-swupdate/rpi5-swupdate-config/files/post-install.sh`
**Issue:** Kernel and DTB handling in OTA updates is complex and may have edge cases.

**Problem:**
- The `.swu` package includes `kernel_2712.img` and `bcm2712-rpi-5-b.dtb` for RPi5/CM5
- pre-install.sh backs up kernel/DTB but if any handler fails, rollback may be inconsistent
- Complex handling may not work for all board types

**Impact:** Kernel updates may require manual intervention on /boot partition if something fails.

**Recommendation:**
1. Test with boards that use different kernel filenames
2. Add error handling for cases where kernel/DTB are missing
3. Document which boards require kernel/DTB in OTA vs those that don't
